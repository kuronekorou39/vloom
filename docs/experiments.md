## 2026-08-28: 格子と解像度の基礎 ([ログ](measurements/2026-08-28.md))

- 格子 × fps の総当たり。**容量は fps でなくセル数で稼ぐ**方針が確定
- **縦長格子の発見**: 受信は縦持ちで視野 3:4。正方形格子は幅で頭打ちになるので、
  縦を使い切る 11×14 で 11×10 を上回る
- 計測の落とし穴 2 つ: カメラ解像度を変えると**画角も変わる** (プリセットは全部 max に統一)、
  **熱でスキャンが 2〜3 倍遅くなる** (温度を揃えないと比較にならない)
- 2bit (輝度 4 値) は容量 2.2 倍だが、レベル間マージン 1/3 で満点ブロック率が落ち、
  同じ格子の 1bit より遅い
- **送信面は平面必須**: 曲面ディスプレイでは四隅からの射影変換が内側で外れ、5 KB/s まで落ちる

## 2026-08-29: コーナーマーカーの大型化 ([ログ](measurements/2026-08-29-marker.md))

- マーカーを 6 → 24 セルへ (4 倍)。追従の既知セルが 16 倍になり、位置合わせが安定
- 追従が切れた後のリトライ (4 フレーム粘る)、AF/AE ロックの功罪 (AF ロックは
  フレーム供給を秒単位で止める → **露出のみ・追従 300 枚後**に)

## 2026-08-30 昼: マーカー直接検出と受信の高速化 (同上ログ後半)

95 → 138 KB/s。効いた順に:

1. **マーカー直接検出** (1/4 縮小画像から 4 種の隅を 6ms で直接探す)。ガイド枠依存が消え、
   構図の自由度が上がった。探索ガイドも「幅基準」→「画角に収まる最大枠」へ
2. 追従の四隅精密化 (descend) が追従時間の 9 割と判明 → **斜め 1/4 間引き + 十字候補**で
   40〜55 → 31ms。rayon 並列化は効かなかった (主因が精密化だったため)
3. スキャンの**同期呼び出し** (非同期の完了通知が UI の描画待ちに掛かっていた)
4. スキャンを**別 isolate へ** (UI isolate はカメラ画像の受け取り専任)。20fps を受信が
   毎秒 22 枚処理できるようになり、13×18 @20fps で 131〜147 KB/s
- 計測ファイルを 100KB → **1MB に標準化** (100KB は 1 秒未満で終わり定常が測れない)
- 露出 −1 EV: 露光が短いほど表示切り替わりの混ざり帯が狭い (LCD)

## 2026-08-30 深夜 〜 31: フォーマット v4 と OLED 送信 ([ログ](measurements/2026-08-30-oled.md))

- **v4: ヘッダを 2×2 セルの太いビットに**。上端を画角の 2% に詰めてもヘッダが読める
  (v3 は 6% で全滅 — レンズ周辺のボケで 1 セルが解像しない)
- **iPhone 12 Pro (OLED) を送信機に**。最初は 14.9 KB/s まで落ちて原因潰し:
  1. **受信 AE が送信画面の周りの黒に騙されて露光 10ms に張り付く** → AE/AF の測光点を
     コード中心に固定 (効果最大。EV への感度がほぼ消えた)
  2. 前後フレームが混ざって灰色に潰れる領域が画面の半分 → Safari の表示向きで差が出る
     謎 (タイル更新と推測) はあったが、本体の向きは無関係と実測で確定
  3. 露光時間の直接指定 (Camera2、1〜8ms) は混ざり帯を細くするが、ゲインのノイズで
     2.3px/セルでは AE に勝てず。**距離が近いほどゲインノイズ・モアレ・歪曲に敏感**
- **レンズ歪曲の壁**: コードが画角の 9 割を占めると、四隅の射影変換だけでは周辺が
  ±1.5 セルずれる (誤差の場を `block_field` で計測 — 中心から外へ線形)。
  → **オフセット伝播** (通ったブロックの隣から外挿して ±0.5 セルだけ試す) で吸収。
  保存フレームで 47 → 150/234、良フレーム 199 → 226
- **モアレ帯域**: 3px/セル前後は送信画面の画素格子をカメラが解像して虹色の干渉縞。
  AF の揺れで出たり消えたり (25〜130 KB/s の振れ)。受信側のぼかしは逆効果。
  内容のぼかしも無意味 (発光素子の格子は物理)。**距離で避ける**
- **30fps で 201〜207 KB/s** (60Hz の 2 書き換えごと。OLED は切り替わりが速く混ざらない)。
  40fps は 60Hz と非整数比で大幅悪化 (100 KB/s) — **60Hz パネルの上限は 30fps**。
  2bit は 4 値が分離できず 0/234 (較正帯太化・ガンマ見直しが要る)
- 運用の教訓: **充電しながらの連続計測は熱制限で復号が 2〜3 倍遅くなる** (big コア
  700MHz 張り付き)。PC の USB 給電では消費に負けて 0% 落ちも。壁充電 + `adb tcpip` で
  Wi-Fi 経由、計測は充電を抜いて冷えた状態で

## 2026-09-06: 手持ちの壁の切り分けと、受信の処理時間

実機を使わずに切り分けるため、合成の計測台を作った
(`cargo run --release -p vloom-vcode --example track_motion -- --grids`)。
手振れ (帯域制限した並進・回転・スケール)、レンズ樽型歪曲、周辺のボケ、
ローリングシャッターの混ざり帯を入れて、実機の動作点 (13x18 で 155/234 ブロック) に
合わせてある。

- **追従は手持ちで切れていない**。14px/0.70deg を振っても 90/90 検出し、回収ブロックは
  三脚比 -0.6% しか動かない。四隅の座標降下に等速外挿を足しても改善しない
  (= 探索範囲は足りている)。手持ちの遅さの原因は追従ではない
- **効いているのはピント**。手振れを固定して中心のボケ半径だけ 0.35 → 0.80px にすると
  13x18 は 190 → 35 KB/s (-82%)、1.20px で 4 KB/s。露光時間 (動きボケ + 混ざり帯) を
  2 倍にしたときの -37% より桁で大きい。据え置きなら AF は一度合えば動かないが、
  手持ちは距離が変わり続けて探り直す — この差だと辻褄が合う
- **崖の位置は px/セル で決まる**。同じ画角で格子を変えると、11x14 (4.19px/セル) は
  ボケ 0.80px でも 101 KB/s を保ち、13x18 (3.38px/セル) だけが崩れる。
  ブロックは 400 セル全部が合って初めて回収できるので、ボケ半径が半セルに近づくと
  満点率が消える。**手持ち前提なら 11x14 のほうが速い**という予測 (要実機確認)
- **ブロック復号のオフセット探索を絞った**。CRC は通ったかしか返さないので、
  外れた候補にも 1 ブロック 400 セルを読む代償を払っていた。CRC の前に間引いたセルで
  閾値からの余裕を測って候補を並べ替え、上位 5 つだけ判定する。
  1 枚 18.3 → 12.2ms (三脚) / 24.6 → 14.9ms (手持ち)、回収ブロックは -0.7%。
  前フレームで通ったオフセットの場も引き継ぐ (場の正体はレンズ歪曲で、フレーム間で
  ほとんど動かない)

### 実機での確認 (Pixel 9a / BenQ 20fps / 1MB)

`tools/measure_rx.py` で 5 本、中央値 **151.7 KB/s** (143.6〜154.5)。
同条件の従来値は 131〜147 (平均 138) なので、オフセット絞り込みのぶんが乗っている。
AF 探り直しは 5 本とも 0 回 = 据え置きでは AF 経路に入らない (狙いどおり)。

途中で 2 つ回り道をした。どちらも「受信側のコードではなく、測り方の問題」だった:

- **アイドル時の CPU 周波数を熱制限と読み違えた**。cpu7 が 700MHz に見えたが、
  負荷をかければ上限の 3105MHz まで上がり `Thermal Status: 0` だった。
  周波数は必ず負荷をかけて読むこと
- **構図が甘いだけだった**。最初の 1 本は 37 KB/s だったが、原因は px/セル 2.96
  (画角の 68%x77% しか占めていなかった)。88% まで寄せて 3.41x3.29 になり、
  回収率が 52% -> 91% に上がった。**px/セル は 3.0 が崖で、下回ると一気に崩れる**

実機のダンプを PC で直接比べる道具も足した (`--example tracked_bench`)。同じ 1 枚で
変更前 4.1ms/枚・回収 122/234、変更後 3.2ms/枚・回収 122/234 と確認できる。
手で構図を再現しなくても、スキャナの変更前後を突き合わせられる。

残りの損失は**送信フレームの切り替わり**。回収ブロックの地図が
「上はフレーム N、下はフレーム N+1、間が死ぬ」形になり、悪い枚では半分を持っていく。
1 本ごとのばらつき (143〜154) もここ。構図では直らない。

### PWA 受信を実機で詰める (Pixel 9a / Chrome / Pages)

「Pages で受信できない」は**古いキャッシュを掴んでいただけ**だった。Service Worker は
新しい資産を取得済みでも、開きっぱなしのページは古い DOM のまま動く。
`adb forward tcp:9222 localabstract:chrome_devtools_remote` + CDP でスマホの
Chrome に繋げば、状態の確認も再読み込みも PC から直接できる (実機を触らずに済む)。

再読み込み後、同じ構図で:

| | 旧 | 新 |
|---|---|---|
| 回収ブロック | 93/234 (40%) | 220/234 (94%) |
| 走査解像度 | 短辺 720px | 1064x1891 (格子に合わせて縮小) |
| px/セル 表示 | 3.9 (実際は 1.5) | 3.6 (実測どおり) |
| 結果 | 永久に終わらない | 復元まで進む |

カメラは 3840x2160 が取れていた (解像度要求を上げた効果)。残る律速は**スキャナ本体**で、
wasm はスレッドが使えず rayon も効かないため 1 枚あたりの計算がそのまま出る。

- **opt-level = "z" -> 3**: 3.6 fps -> **5.9 fps (+69%)**。wasm を 236KB -> 318KB
  にするが、Service Worker が一度キャッシュすれば毎回は落ちてこない。効果最大
- **回転なしの全画素コピーを削除**: 効果なし (5.9 fps のまま)。追従経路では
  1 枚 1 回しか通らず、2MB のコピーは 170ms に対して誤差だった。無駄は消えたが速くならない
- **SIMD128**: 効果なし (むしろ 4.5〜5.3 fps)。セル単位のサンプリングはデータ依存の
  分岐が多く自動ベクトル化が効かない。対応しないブラウザで wasm ごと読めなくなる
  リスクだけが残るので戻した

到達点は 5.9 fps x 約 210 ブロック = **約 50 KB/s** (同条件のネイティブアプリは 140〜150)。
差はほぼ並列度で、次の一手は wasm スレッド (rayon) になる。SharedArrayBuffer には
COOP/COEP ヘッダが要り GitHub Pages では付けられないが、Service Worker で
同一オリジンの応答に付け足す手はある。

注: 連続計測で端末は軽い熱制限 (Thermal Status 1、cpu7 が 3105 -> 2914MHz) に入る。
**CPU 周波数は必ず負荷をかけて読むこと** — アイドル時は 700MHz に落ちていて、
これを熱制限と読み違えた。

### PWA 受信を詰めた結果 (Pixel 9a / Chrome / Pages / 13x18 / 2MB)

端末を触らずに詰められる。`adb forward tcp:9222 localabstract:chrome_devtools_remote`
で CDP に繋げば、状態の確認・再読み込み・受信開始・診断の読み出しが PC から全部できる。

効いた順:

| 施策 | 走査 fps | 備考 |
|---|---|---|
| (出発点: 走査解像度・進捗・Worker 化のあと) | 3.6 | それ以前は復元しない |
| opt-level = "z" -> 3 | 5.9 | wasm 236KB -> 318KB |
| 走査ワーカーを 3 本に | 7.1 | 1 本 -> 2 本が +61%、3 で頭打ち |
| 四隅が合っていれば精密化を省く | **9.4〜9.9** | descend は追従の大きな項 |

端から端まで通した実測は **2.0MB を 49.4 秒 = 41.3 KB/s** (平均 7.3 fps、379/393 枚検出)。
瞬間値 (9.4〜9.9 fps) より低いのは、初回取得と 49 秒ぶんの発熱を含むため。
同条件のネイティブアプリは 151.7 KB/s なので、まだ 3.7 倍の開きがある。

効かなかったもの:

- **回転なしの全画素コピー削除**: 追従経路では 1 枚 1 回しか通らず、2MB のコピーは誤差
- **SIMD128**: セル単位のサンプリングはデータ依存の分岐が多く自動ベクトル化が効かない。
  対応しないブラウザで wasm ごと読めなくなるリスクだけが残るので戻した
- **ワーカー 4 本以上**: Tensor G4 は 大1 + 中3 + 小4 で、速いコアの数で頭打ち

格子の効き方 (擬似カメラ、**フレーム律速**の場合) はブロック数にきれいに比例する:

| 格子 | ブロック | 実効 | 比 |
|---|---|---|---|
| 13x18 | 234 | 276.8 KB/s | 1.00 |
| 11x14 | 154 | 186.4 | 0.67 |
| 9x8 | 72 | 87.6 | 0.32 |
| 7x6 | 42 | 51.3 | 0.19 |

**計算律速**では話が変わる。1 ブロックは格子によらず 400 セルなので、復号のコストは
ブロック数に比例する一方、1 枚あたりの固定費 (マーカー探索・閾値・四隅の照合) は
格子によらない。したがって密な格子ほど固定費が薄まり、**px/セル が足りている限り
密なほうが有利**。粗い格子に落とす意味があるのは px/セル が 3 を割るときだけ。

途中で 2 度はまった罠:

- **Service Worker の addAll はブラウザの HTTP キャッシュを使う**。配信直後に古い応答が
  残っていると新バージョンのキャッシュに焼き込み、「キャッシュは v42 なのに中身は旧版」
  になる。install で `cache: "reload"` を指定して直した。これに気付かず、
  ワーカー本数の掃引を全部同じ設定で回してしまった
- **1 本ごとのばらつきが大きい** (同条件で 3.2〜9.2 fps)。短いサンプルでは
  探している差と区別できない。20 秒待ってから読み、設定が効いていることを
  毎回確認する (診断行に「走査 N 本」を出すようにした)

### 手持ちの遅さは、この構成では再現しなかった (仮説の否定)

合成計測から立てた「手持ちの律速はピント。AF の探り直しを見つけて固定すれば速くなる」を
実機で確かめたが、**前提のほうが再現しなかった**。BenQ ではなく PC のプライマリ
(1920x1080) から 13x18 / 1bit / 20fps で送り、Pixel 9a 手持ちで 1MB を 3 本ずつ:

| 条件 | 中央値 | 範囲 | AF 探り直し |
|---|---|---|---|
| AF固定あり (afhunt 1) | 147.2 | 111.5〜152.7 | 0 回 |
| AF固定なし (afhunt 0) | 139.5 | 130.5〜155.2 | 0 回 |
| (同構成・三脚) | 133.0 | 126.5〜142.1 | 0 回 |

- **手持ちが三脚より遅くない**。むしろ速い。「三脚 138 / 手持ち 60」の落差が出ない
- **AF の探り直しは 12 本すべてで 0 回**。固定機構は一度も発動しておらず、
  2 条件は同じコードを通っている。つまり 147 と 139 の差はすべてばらつき
- **1 本ごとのばらつきが ±15% (111〜155)** で、探している効果より大きい。
  3 本では小さな差を分離できない

したがって AF 固定は、この構成では効果を測れない (発動しないので害もない)。
先に**元の 60 KB/s が出た条件を再現する**必要がある。報告時の送信は Pages (PWA) で、
今回のデスクトップ送信アプリとは別物。次はそちらを揃えて測る。

### 送信側の 2 つの罠 (どちらも黙って数字を壊す)

- **輝度 4 値で送っていた**。デスクトップ送信アプリの bit/セル の既定が
  「2 (輝度4値)」で、`--bpc` を省くと 4 値で送られる。13x18 では回収 0/234 になり
  (2026-08-28 の結論どおり)、「追従中なのに blocks=0」として現れる。既定を 1bit にした
- **1 セルが整数画素で描かれていない**。最近傍拡大なのでセル幅が 2px と 3px に混ざる。
  同じ窓・同じ zoom でも格子で端数が変わる (13x18 は 2.07px/セル、11x14 は 2.52 =
  整数から最も遠い) ため、**格子どうしの比較が端数の比較になる**

整数化 (`--snap`) を入れて 13x18 で 3 本ずつ比べたが、**差は出なかった**:

| | px/セル (画面) | コード高 | 中央値 |
|---|---|---|---|
| 端数あり | 2.32 | 965px | 133.2 (127.7〜137.5) |
| 整数 | 2.00 | 832px | 133.0 (126.5〜142.1) |

整数化で 14% 小さくなるぶんと、端数の乱れが消えるぶんが釣り合っている。
**効いていたのはコードの大きさのほう**で、同じ構成で zoom を 0.92 → 0.82 に
落としただけで 133 → 78.7 KB/s まで落ちた。--snap は残してあるが既定は従来のまま。

### PWA の受信が終わらなかった件

Pages の受信は 13x18 で永久に完了しなかった。原因は 3 つとも受信側:

1. 縮小を「長辺 1280px」で切っていた。vcode は縦長 (13x18 で 260x416 セル) なので
   効くのは短辺で、1920x1080 のカメラは 1280x720 に落ちて 1.5px/セル。毎フレーム
   検出には成功するのに 234 中 55 ブロックしか回収できず、同じ 55 が延々と返って
   必要パケットに届かない。→ 選んだ格子が要求する px/セル を満たすところで縮小を止める
2. 進捗が frames と検出回数だけだった (どちらも増え続けるので 1 の状態が
   「順調に見えて終わらない」)。→ 重複を除いたパケット数 / 必要数 とバー、
   6 秒増えなければ原因を名指し
3. px/セル の診断が長辺 x 格子の幅 で計算されていて、13x18 では実際の 2.6 倍を
   表示していた (1.5 なのに 3.9)。→ 短辺 x 縦のセル数 で計算し直し

擬似カメラ 1920x1080・1MB で 13x18 が 143 KB/s (走査 37.6fps) まで通るようになった。
回帰テスト (`tools/test_pwa_receive.py`) も、擬似カメラを実機と同じ 1920x1080 で
作るように直した (以前は 650x1040 の小さな映像で、解像度不足を再現できていなかった)。

## 2026-10-05: ブロック内の誤り訂正は要るか / 湾曲モニター ([ログ](measurements/2026-10-05-block-errors.md))

「ブロック内に軽い誤り訂正を入れれば px/セル の崖が緩む」という案を、形式を変える前に
保存フレームで確かめた。送ったファイルから正解のビット列を作り直し、CRC に落ちたブロックが
何ビット外していたかを数える (`--example block_errors`、標本は `--ei dumpall` で等間隔に取る)。

- **形式に誤り訂正を入れても平面では得にならない**。1 ビット誤りのブロックは全体の
  2〜3% あるが、全ブロックが払う検査ビットで相殺される (3 ビット訂正で正味 0.96〜0.97 倍)。
  固定でも手持ちでも同じ。「読めなかった枚」だけで見積もると 1.26 倍と出るので、
  標本の取り方に注意
- **湾曲モニターで読めなかった主因は、曲がりではなく輝度の勾配**。白のレベルが上端 95 /
  下端 195 と 2 倍違い、全体で 1 つの閾値では上端が丸ごと黒になっていた
- **二値化の閾値を 2 段にした**: (1) 上下ストリップから行方向に補間、(2) それで CRC が
  通らないブロックは、そのブロックの 400 セルだけの Otsu 閾値で読み直す。
  同じ画像での回収率が、平面の固定 86.8% → 91.4%、手持ち 91.0% → 94.0%、
  湾曲 0% → 87.0%。処理時間は変わらない。**湾曲の実機は検出 0 → 中央値 130.8 KB/s**
  (5 本、123〜143) で平面と並んだ
- 「1 ビットだけ外れたブロック」の大半は閾値の置き場所の問題で、ブロックごとの閾値で
  消えた (283 → 40)。誤り訂正や「怪しいセルの反転」で拾える残りはわずか
- **px/セル の崖が 3.0 から 2.5 前後へ動いた**。2.7 px/セル で中央値 149.3 KB/s (5 本、
  3.05 px/セル と同じ速さ。同じ画像の回収率は 79.3% → 90.6%)。2.4 px/セル は 28% でまだ無理。
  合成計測は「ボケの崖が消える」と出たが (ボケ 0.80px で 33.5 → 175 KB/s)、実機はそこまで伸びない
- **マーカー直接検出の取りこぼしを直した** (2026-10-06)。1 枚ずつ独立に検出させると、
  手持ちで 16/42 枚、15x20 で 0/10 枚しか四隅が出ていなかった (普段は追従に隠れて
  見えない)。縮小画像で候補を拾ってから元の解像度で合わせ直す 2 段にし、外周の黒さの
  条件を緩め、「周囲は 4 辺とも白」を足して、標本 239 枚すべてで通るようになった
  (変更前 182 枚)。初回取得の遅さに効くはずだが、実機での確認はまだ
- 効かなかったもの: 上下ストリップで測ったずれをオフセット候補にする (位置は足りていた)
- どの条件でも残る最大の損失は、従来どおり切り替わりの混ざり。前後どちらかの枚が既知なら
  落ちたブロックの 8 割は読める (平面で回収率 98% 台) という上限だけ確認した。実際に
  既知の側が手元にあるかは、連続した枚の標本で確かめる必要がある

## 2026-10-06: 「さがす」モード (設定を自動で切り替えて速さを測る)

条件を 1 つ変えるたびに送受信を起動し直すのをやめて、送信側が格子と fps の組を 4 秒ずつ
切り替えながら試験フレームを流し、受信側が設定ごとの実効スループットを出し続ける形に
した (`vcode::probe`、送信は `python -m desktop --sweep`)。ファイルは運ばず、
「重複なしで読めたブロック数 × 42 バイト ÷ 写っていたフレーム数ぶんの時間」を数える。

- 受信側は格子を知らされない。マーカーの写り (大きさと縦横比) から格子を言い当てる
  処理を足し、標本 239 枚すべてで一発で当たった。切り替えには数枚で付いていく
- 数字は本番の転送とおおむね合う: 13x18 / 20fps が 145〜155 (本番 149〜156)、
  15x20 / 20fps が 141〜165 (本番 164〜180)
- **fps も同じ仕組みで探せるが、30fps は巡回ごとに大きく振れる。** 13x18 / 30fps は
  110〜207 KB/s。送信 fps がカメラの fps (30) と近く、切り替わりと撮影の噛み合わせ次第で
  混ざる帯の広さが変わるため。20fps は 137〜157 に収まる。そこで一覧には最小〜最大を
  出し、「おすすめ」は悪かった巡回の値で選ぶ
- 試せる fps は画面の書き換え周期を割り切れる値だけ (60Hz なら 15 / 20 / 30)。
  送信側が周期を読んで候補を決める。60fps は 137 KB/s で 20fps より遅い
- 4 秒の試験では熱の影響が見えない。連続で回すと端末が熱制限に入り (Thermal Status 1、
  スキャン 21 → 62ms)、密な格子から先に落ちる

## 2026-10-06: 混ざりの救済は効かず、律速は処理枚数だった ([ログ](measurements/2026-10-05-block-errors.md))

「切り替わりで混ざったブロックは、片方の枚が既知なら 8 割読める」という上限を、連続した
80 枚の実機ダンプで「受信側が実際に持っているものだけ」で再現した。増えたのは
**+0.6〜1.5%**。救えるブロックの多くは別の枚で既に取れているか、既知の側が手元に無い。

代わりに分かったこと: 送信 30fps のとき、処理した 1 枚は平均 217 ブロック (93%) を新しく
持ち帰っていた。**実効 KB/s ≒ 8.9 × 1 秒に処理した枚数** で、今は約 20 枚/秒 = 180 KB/s 台。
カメラの 30 枚/秒を全部処理できれば 267 KB/s になる計算。LCD で 200 を安定して超える
道は、混ざりの救済ではなく受信の処理枚数。

### スキャンを 2 本で並行に回す (同日)

上の仮説をそのまま試した。走査ワーカーを 2 本にすると処理が 21 → 26 枚/秒に増え、
本番の転送 (2MB、13x18、3 本ずつ) の中央値が **20fps で 148 → 166 KB/s、30fps で
136 → 217 KB/s**。LCD でも 30fps が 203〜220 に収まり、1 本のときの当たり外れ
(119〜207) が消えた。3 本は 2 本と変わらない (カメラが毎秒 30 枚強)。
既定はまだ 1 本 (`--ei workers 2` で切り替え)。手持ち・長い転送・遅い端末を確かめてから。

## 2026-10-19: 走査 2 本を既定に / 長い転送は熱制限で半分の速さ ([ログ](measurements/2026-10-19-workers-heat.md))

10MB を 13x18 / 30fps (LCD) で、1 本と 2 本を交互に 6 回、冷却なしで続けて送った。

- **2 本は 6 回とも前後の 1 本より速い** (中央値 86.9 対 82.4 KB/s)
- **温度は本数で変わらない。** 表面は 42°C 前後で頭打ちになる。熱制限が CPU を抑えるので、
  2 本にしても発熱の上限は同じ
- そこで**既定を 2 本にした**。遅い端末は未確認

ただし、**長い転送はどちらでも 75〜103 KB/s** で、2MB (150〜220) の半分程度だった。
開始から約 2 分で熱制限に入り、スキャンが 2 倍近く遅くなる。2MB は熱が入る前に終わる。
送信側の生成 (1 フレーム 0.7 ms) は原因ではない。

同じ日に三脚を近づけ (充填 高さ 77 → 84%、2.9 → 3.2 px/セル)、毎回冷ましてから 10MB を送った。
**13x18 は近づけても約 100 KB/s で変わらない**が、同じ構図で **15x20 (2.8 px/セル) にすると
130 KB/s (+29%)**。処理できる枚数は同じ毎秒 26〜27 枚で、1 枚で運ぶブロックが増えたぶんが効く。
熱で処理枚数が頭打ちになる長い転送ほど、格子の密度が効く。

カメラの fps を Camera2 で [30, 30] に固定しても変わらなかった。プラグインの `fps: 30` で
最初から [30 30] になっていた。「カメラ実効fps 45」はアプリの数え方の問題で、撮りすぎてはいない。

## 所要時間の目安に使っている実測値

送信画面の「所要時間の目安」は理論値ではなく、ここまでの実測の中央値から出している。
理論値 (ブロック数 × packet_size × fps) は取りこぼしも RaptorQ の冗長も含まないので、
時間に直すと必ず短く出る (13x18 @20fps は理論 192 KB/s に対して実測 151.7)。
送信側は受信できたかを知る手段がないので、その場の実測は使えない。

| 受信 | 格子 | 送信 fps | 実効 KB/s | 出どころ |
|---|---|---|---|---|
| アプリ | 5x4 | 20 | 9.5 | 2026-08-28 (10.5 / 8.4) |
| アプリ | 7x6 | 20 | 22.0 | 2026-08-28 (21.7 / 22.2) |
| アプリ | 9x8 | 20 | 39.5 | 2026-08-28 (37.7 / 41.2) |
| アプリ | 11x10 | 20 | 60.0 | 2026-08-28 (60.3 / 59.6) |
| アプリ | 11x14 | 20 | 80.5 | 2026-08-30 格子の天井 (76.7 / 89.5 / 80.5) |
| アプリ | 13x18 | 20 | 151.7 | 2026-09-07 LCD 送信、5 本 |
| アプリ | 13x18 | 30 | 204 | 2026-08-31 OLED 送信 (201〜207) |
| ブラウザ | 13x18 | 20 | 41.3 | PWA 受信、2.0MB を 49.4 秒 |

値の写しは `web/pwa/estimate.js` (MEASURED) と `app/lib/preset.dart` (kMeasuredKbps) の
2 か所にある。更新するときは、この表を先に直してから両方を揃える。

限界として知っておくこと:

- **粗い格子 (5x4〜11x10) の値は古い**。マーカー直接検出や受信の高速化より前の計測で、
  しかも 100KB (定常に入る前に終わる) なので、今の実力より低く出ているはず。
  目安としては長めに出る側に倒れる。測り直したら差し替える
- fps が測ったときと違う設定は、最も近い実測から fps に比例させている。60Hz 画面の上限
  (30fps) を超えるぶんは伸びに数えない。ブラウザ受信は走査の速さが律速なので、
  送信 fps を上げても増やさない
- ブラウザ受信の 41.3 は送信 fps の記録が残っていない (20 として扱っている)
- 18x13 と輝度 4 値は実測が無い (または安定しない) ので、目安を出さない
- すべて三脚固定・Pixel 9a。1 本ごとに ±15% ばらつく

## 開いている課題

- **長い転送の熱制限**: 10MB は開始 2 分ほどで熱制限に入り、2MB の半分の速さになる
  (2026-10-19)。送信画面の所要時間の目安は 2MB までの実測なので、大きいファイルでは
  短く出すぎる。20fps の長い転送と冷却条件を測ってから、目安にサイズの補正を入れるか決める。
  受信側で熱を減らす手 (同じ送信フレームを二度処理しない、など) も候補

- **手持ちのピント (実機で裏取り待ち)**: 合成計測の結論を受けて、受信に
  「満点率が高い → 低い → 高い を 2 度観測したら AF が探り直していると見なし、
  次に高くなった瞬間 (= 今合っている) に AF を固定する」経路を入れた。
  三脚では満点率が落ちないのでこの経路に入らない = 従来の実測
  (both 49 / ae 76 KB/s、モード切替の停止だけが乗る) を壊さないはず。
  `tools/measure_rx.py --arm "AF固定あり:--ei afhunt 1" --arm "AF固定なし:--ei afhunt 0"`
  で A/B できる。あわせて、回収率が 35% を下回り続けたら 11x14 を勧める誘導も入れた
- 90°/270° 回転の常時対応 (横に構えると掴めない) — 次の開発テーマ
- 2bit の再設計 (較正帯太化 + ガンマ + モアレの出ない距離)
- 120Hz パネルでの 40〜60fps
- カメラ画像の受け渡しコスト (UI isolate の 20ms/枚) — 効けばネイティブ CameraX 直結
- レンズ歪曲の明示的なモデル化 (伝播で当面は足りている)
- より密な格子: 15x20 は 13x18 より約 11% 速い (中央値 170.3 対 152.9 KB/s)。
  16x22 は測れていない (送信側が一辺 20 に黙って丸めていた。範囲外はエラーにした)。
  手持ちでは逆に 15x20 が遅い (42.8 / 95.4 対 130.4 / 108.1)。回収率は高いのに
  スキャンが 81〜113ms に延びる — 手持ちの律速は四隅の精密化の処理時間。
  スマホ送信の標本 — 2026-10-05 のログの「次」
