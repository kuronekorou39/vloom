# 2026-08-30 OLED (iPhone 12 Pro) を送信機にする実験 — 準備

## ねらい
BenQ (LCD) では、表示の切り替わりがローリングシャッターの 1 枚に混ざる帯と、液晶の応答の
遅れで、20fps でも約 5% のフレームが捨てられていた。OLED は画素の応答が 1ms 未満なので、
この帯が消えるはず。iPhone 12 Pro (OLED、1170x2532、DPR 3、460ppi、60Hz) を送信機にし、
Pixel 9a (アプリ) で受ける。

## 送信側 (PWA) の変更
- キャンバスの裏バッファを端末の物理画素に合わせ (CSS px × DPR)、1 セルを整数個の物理画素
  で描く。以前は 1080x1080 固定を CSS で拡縮していて、セル境界が画素にまたがってぼけていた
- フレームの切り替えを requestAnimationFrame に (経過時間から番号を決める)。60Hz なら
  20fps は 3 回の書き換えごとに 1 フレームで、切り替えが vsync に揃う
- Screen Wake Lock で消灯を止める。大きさ (%) / 静止 / バー非表示 (コードをタップ) を追加
- 13x18 は 260x416 セル → iPhone 12 Pro で 4px/セル = 1040x1664px = 57x92mm

## 手順
1. PC: `python web/pwa/serve_https.py` (LAN に HTTPS 配信、自己署名)
2. iPhone (同じ Wi-Fi) の Safari で `https://192.168.11.52:8443/index.html`
   → 証明書の警告で「詳細を表示」→「この Web サイトを閲覧」。
   共有 → ホーム画面に追加 で全画面にするとツールバーぶん広く使える
3. iPhone の設定: 明るさ最大、自動明るさ / True Tone / Night Shift オフ、縦向きロック、
   低電力モードオフ
4. 送信: ファイルに test-1MB.jpg (PC から AirDrop するか、テキストで代用)、13x18 / 1bit / 20fps
5. 受信: Pixel 9a を三脚で iPhone に正対させる。カメラの 1 画素が 0.074mm になる距離
   (約 9〜10cm) で 3px/セル、約 14cm で 2px/セル。Pixel 9a はメインカメラでマクロ
   フォーカスが効くので近くても合う。受信アプリの読み上げ (充填/余白/px/セル) で確認
6. 計測は BenQ のときと同じ (1MB、[vloom-stats]、温度は HAL)

## 比較したいこと
- 同じ px/セルでの回収率 (BenQ 95〜97%) と、捨てたフレームの帯の有無 (blockmap)
- fps を 20 → 30 に上げられるか (BenQ では 20 が最良)
- 輝度: OLED は白が暗め (iPhone 12 Pro 最大 800 nit) なので露出 −1EV のままで足りるか

## 結果 (2026-08-31 深夜、iPhone 12 Pro → Pixel 9a 三脚固定、13x18 / 1bit / 20fps / 1MB)

| 条件 | 1 枚あたり (/234) | 9 割以上読めた枚数 | 1MB |
|---|---|---|---|
| EV −1 (BenQ の既定のまま) | 117 (50%) | 0% | 69 秒、14.9 KB/s |
| EV −2.5 | 184 (79%) | 10% | 8.0 秒、128 KB/s |
| AE 測光点をコード中心に、EV −1.5 | 187 (80%) | 35% | 8.2 秒、125 KB/s |
| 同上、Pixel を置き直したあと (2.3px/セル)、Safari 縦表示 | 185〜190 | 30% | 7.3〜7.6 秒、136〜141 KB/s |
| 同上、**Safari だけ横表示** (本体は縦のまま、PWA がコードを回すので画面上のコードは縦長・180°) | **203〜215 (87〜92%)** | **78%** | **6.4〜6.9 秒、149〜160 KB/s** |

分かったこと (順に潰した):

1. 受信アプリを手で起動すると既定の 7x6 になっていて掴めなかった (Intent で 13x18 を指定)
2. **自動露出が iPhone の周りの黒に引っ張られる**。BenQ は画角いっぱいが白だったので気付かなかった。
   AE が画面全体の平均を目標まで上げようとしてコードの白が飽和し、露光が伸びて切り替えの混ざりが
   広がっていた。EV を −2.5 まで下げると改善するが、根本対策は AE/AF の測光点を画角の中心
   (= コード) に置くこと (setExposurePoint/setFocusPoint、Intent aepoint=none で外せる)。
   これで EV への感度がほぼ消えた (−1〜−2.5 で 149〜160 KB/s)
3. 読めないフレームを保存して見ると (Intent dump=N)、マーカーは鮮明なのにデータ部だけ前後フレームが
   混ざって灰色に潰れており、その領域が斜めの境界で画面の半分に及ぶ。当初「縦持ち同士では画面の
   書き換えとローリングシャッターが平行だから」と考え送信端末を横向きにする案を出したが、
   **本体を動かさず Safari の表示だけ横にしても同じ改善が出た** (上表の下 2 行、同じ置き方で
   136〜141 → 158 KB/s) ので、本体の向きは原因ではない。訂正。
   横表示のときの失敗フレームは、混ざった灰色ではなく「白く抜けた帯」で、Safari が回転した
   ページをタイル単位で更新している (切り替えが領域ごとにずれる) ためと推測。根本は受信の
   露光時間が切り替えの混ざりに対して長いことで、次の一手は受信側で露光時間を直接指定する
   (Flutter の camera プラグインには無いので、ネイティブ (CameraX + Camera2Interop) が要る)
4. 18x13 (横長格子) はマーカー帯が上下にしかないためほぼ正方形 (360x316 セル) で、横画面では
   高さで頭打ち (3px/セル)。横長のフォーマットを作るより、縦長コードを回すほうが得
5. Pixel 9a は PC の USB (5V/1.5A、発熱時はさらに制限) では受信中の消費に負けて 0% まで落ちた。
   壁の充電器 + `adb tcpip 5555` (Wi-Fi 経由の adb) で計測する
6. 余談: SHV48 (AQUOS、Snapdragon 630) でも lab 版が動き、iPad の PWA から手持ちで 2MB を
   120 秒で復元できた (約 17 KB/s)。掴む前の全画面探索は 1.6 秒/枚と重い

残り: 20fps の生レート 197 KB/s に対して 150〜160 なので、損失は切り替えの混ざり (1 枚あたり
約 10%) と取得の立ち上がり。次は (a) 受信の露光時間の直接指定、(b) 送信 30fps。
