# 2026-11-27 色を使う価値があるか (セルの読み誤りを直接数える)

カメラ直結 ([2026-11-26](2026-11-26-native-camera-probe.md)) で 30MB が 64〜68 秒まで縮んだあと、
次に「色で 1 セルあたりのビットを増やす」が効くかを、形式に手を入れる前に確かめた。

## やり方

vcode とは別の、答えの分かっている模様を画面に出し、カメラの生画像 (Y・U・V) と突き合わせて
セルごとの読み誤りを数える。道具は `tools/color_probe/`。

- `patterns.py`: 模様。白黒 (2 色) と、RGB の各チャネルを 0 / 255 にした 8 色 (1 セル 3 ビット)。
  画面中央の 1152x900 画素をデータ領域にし、四隅に黒い目印を置く (横長の 30x20 を全画面で
  出したときとほぼ同じ大きさ)
- `show.py`: 模様を全画面で出す
- 撮影: 試作アプリ (profile ビルド) の `ProbeActivity` に `--ei dumpyuv N` を足し、Y・U・V を保存
- `analyze.py`: 目印から射影を決め、升目ごとに明るさの相関でずれを合わせ、セルの中心を読む。
  記号の当て方は 2 通り: 平均色にいちばん近いもの (centroid) と、周り 8 セルも見る線形の判別
  (equalizer)。升目の半分で学習し、残り半分で誤りを数える

```bash
uv run --group desktop --group dev python tools/color_probe/show.py rgb8_c2 --screen 2
adb shell am start -n app.vloom.vloom.probe/app.vloom.vloom.ProbeActivity \
    --ei w 2560 --ei h 1920 --ei fps 30 --ei dumpyuv 3 --ei exp 8000 --ei iso 55
adb pull /sdcard/Android/data/app.vloom.vloom.probe/files/ out/
uv run --group dev python tools/color_probe/analyze.py rgb8_c2 out/files/yuv_*.bin
```

**甘い数字が出る測り方**であることに注意。静止画で、答えを使って位置を合わせ、同じ画像で
学習している。実際の受信 (表示が切り替わる・位置は自力で合わせる) はこれより悪い。
白黒も同じ手順にかけてあるので、白黒と色の**差**を見る。

## 条件

- 送信: BenQ (1920x1080)、全画面、静止
- 受信: Pixel 9a を横向きで固定。データ領域は画像の幅の約 7 割 (画面 1 画素 ≈ カメラ 1.56 画素
  @2560x1920、2.4 画素 @4000x3000)
- 露光 8000µs・ISO 55 に固定 (白が Y=112 前後)。自動露出のままだと白が 240 前後で飽和し、
  色の誤りが 4〜8 倍に増えた (緑・黄・水色が白に潰れる)
- 模様ごとに 3 枚 (白黒の追加分は 2 枚)。同じ模様の 3 枚は誤り率がほぼ同じだった

## 結果

誤り = 記号を取り違えたセルの割合 (2 通りの当て方の良いほう)。ブロックが通る割合は、
400 セルが全部合う確率 (1 − 誤り)^400。

| 模様 | 1 セル (画面 / カメラの画素) | 誤り | ビット別 (R / G / B) | ブロックが通る割合 |
|---|---|---|---|---|
| 白黒 | 2 / 3.1 | 0.0000 (約 13 万セルで 0〜数個) | — | 1.00 |
| 8 色 | 2 / 3.1 | 0.151〜0.154 | 0.048 / 0.0000 / 0.110 | 0 |
| 8 色 | 3 / 4.7 | 0.020〜0.023 | 0.007 / 0.0000 / 0.015 | 0 |
| 8 色 | 4 / 6.2 | 0.011〜0.013 | 0.004 / 0.0000 / 0.008 | 0.005〜0.012 |

白黒をさらに細かくした場合 (追加):

| 模様 | 撮影 | 1 セル (画面 / カメラの画素) | 誤り | ブロックが通る割合 |
|---|---|---|---|---|
| 白黒 | 2560x1920 | 1 / 1.56 | 読めない (位置も合わない) | 0 |
| 白黒 | 4000x3000 | 1 / 2.4 | 0.0009 (equalizer)、0.0068 (centroid) | 0.69 (equalizer) |
| 白黒 | 4000x3000 | 2 / 4.9 | 0.0000 | 1.00 |

## モニタのせいではないか (同日の確認)

BenQ は色が飛んで見えることがあり、キャプチャーボード (AVT GC553) 経由でつながっている。
モニタに届く前に色が間引かれている (YCbCr 4:2:2 など) なら、上の結果はモニタの問題になる。

- PC の出力は RGB・フルレンジ (dxdiag の Display Color Space)。ただしキャプチャーボードから先は
  PC からは見えない
- 赤と青の 2 画素幅の縞を、2 画素の区切りに合わせたものと 1 画素ずらしたものとで出した
  (`show.py stripes`)。色を間引く経路なら、ずらしたほうだけ紫一色になる。実際は、ずらしたほうの
  色の振れが 25〜35% 弱い程度で、横にも縦にも同じように出た。間引きの形ではない。ただ、どの縞も
  ほとんど紫に混ざって写っていて (カメラ側の色の解像度が足りない)、カメラだけでは切り分けきれない
- そこで、DisplayPort で直結している MSI (MAG321CQR、2560x1440、湾曲) に同じ模様を等倍で出して
  測り直した。4000x3000 で撮影 (画面 1 画素 ≈ カメラ 1.9 画素。BenQ を 2560x1920 で撮ったときの
  1.56 より細かく写っている)、露光は同じ、各 2 枚

| 模様 | 1 セル (画面の画素) | BenQ の誤り | MSI の誤り | MSI のビット別 (R / G / B) |
|---|---|---|---|---|
| 白黒 | 2 | 0.0000 | 0.0003〜0.0005 | — |
| 8 色 | 2 | 0.151〜0.154 | 0.295〜0.303 | 0.09 / 0.005 / 0.23 |
| 8 色 | 3 | 0.020〜0.023 | 0.116〜0.119 | 0.02 / 0.0002 / 0.10 |
| 8 色 | 4 | 0.011〜0.013 | 0.075〜0.086 | 0.015 / 0.0002 / 0.07 |

**直結の MSI のほうが色は悪かった。** BenQ の経路が原因ではない。明るさ (緑) は読めて赤と青が
読めない、という形は 2 台で同じで、原因はカメラ側 (と、画面の画素の並び) にある。MSI は白い面に
緑がかった縞 (モアレ) も出ていた。

## 分かったこと

- **色は割に合わない。** 緑のビット (明るさとほぼ同じ) は色を乗せても完璧に読めるが、赤と青の
  ビットは今の細かさ (画面 2 画素) で 5〜11% 間違える。4 倍の面積 (画面 4 画素) まで粗くしても
  0.4〜0.8% 残り、400 セルのブロックはほぼ通らない。粗くしたぶん載る量は 3 ビット ÷ 4 = 0.75 で、
  誤りが 0 だったとしても白黒の 2 画素 (1 ビット) に届かない
- 原因はカメラ側。色差は縦横半分 (YUV 4:2:0) で、画像処理が色のノイズをならすので、セルの
  境目で色が混ざる。露出を合わせても変わらなかった
- 色を粗い格子 (4 画素) に、明るさを細かい格子 (2 画素) に分ける案なら、理屈の上では +0.5 ビット
  /セル (+50%)。ただし色の層は 0.4〜0.8% の誤りを直す符号が要り、黒いセルには色を乗せられない。
  以前の検証ではブロック内の誤り訂正は正味 0.96〜1.01 倍だった ([10 月](2026-10-05-block-errors.md))。
  見込める上積みは 2〜3 割で、形式を 2 層にする手間に見合わない
- **白黒のまま細かくするほうが筋がいい。** 4000x3000 で撮ると、画面 1 画素のセル (今の 4 倍の数) が
  誤り 0.09% で読め、ブロックの 7 割が通る。1 枚あたり約 2.8 倍 (4 × 0.69) 載る計算になる。
  ただしこれは周りのセルも見る読み方 (equalizer) での値で、素朴な読み方だと 0.68% (ブロックは
  7% しか通らない)。今のスキャナがどちらに近いかは、実際の vcode で測らないと分からない
- 2560x1920 のままでは、画面 1 画素のセルは読めない (カメラ 1.56 画素/セル)
