# コーナーマーカーの大きさ (2026-08-29, Pixel 9a / BenQ / 100KB)

マーカーの一辺を 6 / 12 / 18 / 24 セルで振った (セパレータも 1 / 2 / 3 / 4 セルで
比例させた)。送信 20fps、リペア 50%、余白 8 セル、受信 1600×1200、送信ウィンドウは
横長 (664,6,1199,881) のまま。ヘッダ/較正はマーカーの高さに関わらず 8 行に固定
(BAND_ROWS)。11×14 は横長ウィンドウでは高さが上限になり、11×10 より小さく写る。

条件ごとに Rust の定数を書き換えて送受信の両方をビルドし直している (1 条件 2 分)。

| 6 | 59.0 / 64.5 | 17.9 / 65.9 |

| 24 | 31.6 / 63.6 | 67.7 / **84.8** |

**同じ条件で 18 と 66、70 と 19 のように二極化しており、セル間の差よりセル内の
ばらつきが大きい。** この表だけではマーカーの最適値は決められない。速い側と遅い側で
検出枚数はほぼ同じ (26 前後) なのに所要時間が 4 倍違うので、「検出が疎になる」
モードがある。その正体はフレーム単位のログ (measure.py が `.log` に残す) で追う。

## 再現性の確認 (11×14 / コーナー 24 / 20fps、5 本連続)

57.9 / 74.5 / 44.8 / 44.1 / 53.9 KB/s (平均 55)。スイープで出た 18〜19 KB/s の
「遅いモード」はこの 5 本では出なかった。フレームごとのログ (`.log`) から分かったこと:

- **追従中の scan は 40〜60ms** で、カメラの 25fps にほぼ追いつく。統計の「平均
  スキャン時間」110ms は取得 (acquire) の 160〜210ms と未検出フレームを含めた値で、
  追従の実力を表していない。セル数に比例して重いのは取得のほうで、追従はずっと軽い。
- 支配的なロスは**「半分未満」のフレーム**。追従できた枚数の 3〜4 割が 60〜70/154
  (約 45%) しか取れない。20fps 送信 × 25fps カメラの位相ずれで、1 枚の中に表示の
  切り替わりが入っている (ローリングシャッター)。
- 追従が 1 回外れると即フル探索 (160〜210ms) に落ち、その間に 4〜5 枚落ちる。
  実測で 500〜600ms の空白が 2 秒の受信の中に出ていた。三脚固定では四隅は動いて
  いないので、切り替わりの帯がマーカーにかかった 1 枚で諦めるのは損。数枚は同じ
  四隅で粘るよう受信側を直した (`TRACK_RETRY_FRAMES`)。

```

  0.19        72    10    +2   71/154   59ms  追従  <- 半分未満
  0.37        61    14    +2   66/154   41ms  追従  <- 半分未満
  ...
  2.22       591    24    +8  137/154  196ms  取得    <- 追従が切れて取得に戻る
```

| fps | 9×12 | 11×14 | 13×16 |

- **11×14 が圧倒的に安定**。8 本すべて 66 以上で、15〜20fps では 78〜98 KB/s。
  同じ構図で 11×10 / コーナー 6 が 60 KB/s だったので、縦長格子 + 大マーカーで
  1.4〜1.6 倍になった。
- 満点率は fps を下げるほど上がる (12fps で 68%、20fps で 11〜45%)。1 枚の中で
  表示が切り替わる確率が fps に比例するという読みと一致する。ただし枚数が減るぶん
  スループットは 15〜20fps のほうが高い。部分回収があるので混ざったフレームも
  無駄にはならない。
- 13×16 は 260 セル幅で 3px/セル 程度になり、満点 0%。稀に通る (95.0) が実用外。
  幅を広げる方向は今の構図では頭打ち。
- 9×12 は二極化 (9〜17 と 31〜59)。1 枚の容量が小さい (4,536 B) うえ不安定で、
  11×14 に対して利点がない。

## 追従リトライの A/B と、その裏で見つかったカメラロックの停止

11×14 / コーナー 24 / 20fps で、追従が 1 回外れてもフル探索に落ちず 4 枚粘る版
(`TRACK_RETRY_FRAMES`) を 5 本: 33.3 / 61.3 / 21.1 / 87.2 / 27.9 KB/s (平均 46、
対照 55)。**悪化して見えるが、フレームログを見るとリトライは無関係だった。**

```
01:05:06.837 camera lock (AF/AE)     <- 15 枚連続検出で AF/AE を固定
01:05:07.535 seq=22 ... tracked=true
   (3.0 秒間フレームが 1 枚も来ない。未検出ログすら出ない)
01:05:10.584 seq=11 ... tracked=false
```

追従が安定したときに AF/AE を固定する処理 (`kCamLockStreak = 15`) があり、この
モード切替が**カメラのフレーム供給を 0.5〜3 秒止める**。空白の間はスキャン自体が
走っていないので、スキャン側の改善は効かない。止まる長さが回によって違うのが、
これまで「同じ条件で 18 と 66」のように二極化して見えた原因と考えて辻褄が合う。

ロックは手持ちでピントが泳ぐのを防ぐためのものだが、三脚固定の 100KB 転送
(1.5 秒) では 3 秒の停止と釣り合わない。何を固定するか (none / ae / both) を
起動 Intent で切り替えられるようにし、次の節で比べる。

## カメラロックの比較 (11×14 / コーナー 24 / 20fps、各 4 本、ランダム順)

| ロック | 実効 KB/s | 平均 | 500ms 超の空白 |
|---|---|---|---|
| none | 58.3 / 76.5 / 68.3 / 81.5 | 71.2 | 0 |
| **ae (露出のみ)** | 69.5 / 59.9 / **110.9** / 63.8 | **76.0** | 0 |
| both (従来: AF + AE) | 14.2 / 79.8 / 66.4 / 36.8 | 49.3 | 5170ms、1202ms |

**フレーム供給を止めていたのはピント (FocusMode) の切替**で、露出 (ExposureMode) の
固定は止まらない。露出の固定には白飛びを防ぐ効果があるので、既定を `ae` にした。
`both` の 14.2 KB/s は 5 秒止まった回で、これがこれまでの「遅いモード」の正体。

110.9 KB/s は 11×14 / 20fps / 露出のみ固定で出た現時点の最良値。

## 追従リトライの A/B (露出のみロックで取り直し、各 5 本)

| | 実効 KB/s | 中央値 | 最小 |
|---|---|---|---|
| リトライ 4 枚 | 70.0 / 28.6 / 77.1 / 69.6 / 73.1 | **70.0** | 28.6 |
| リトライなし (従来) | 66.5 / 61.0 / 27.4 / 56.2 / 74.9 | 61.0 | 27.4 |

中央値で 15% ほど有利、副作用なし。`TRACK_RETRY_FRAMES = 4` で採用。

両群に 1 本ずつ 1.65〜1.7 秒の空白が残っており、`camera lock (ae)` の直後に出て
いる。**露出ロックも (AF より頻度が低く短いが) フレーム供給を止める。** カメラの
モード切替は何であれ受信中に入れるべきではない。露出の固定には白飛び防止の意味が
あるので捨てずに遅らせ、`kCamLockStreak` を 15 → 100 枚 (約 5 秒) にした。
100KB 級 (25 枚で完了) では発動せず、数 MB の転送だけが 1 回の停止と引き換えに
露出の安定を得る。

## この日の結論

| 項目 | 判定 | 根拠 |
|---|---|---|
| 縦長 11×14 | 採用 | 8 本すべて 66 以上、最良 111 KB/s (11×10 は 60) |
| コーナー 24 セル | 採用 (11×14 向け) | 11×14 で 18 → 68〜85。11×10 では 6〜12 が最良で逆効果 |
| 送信 15〜20fps | 採用 | 12 は枚数不足、25 はやや劣化 |
| 受信中のカメラロック | 遅らせる | AF は 1〜5 秒、露出も 1.7 秒止める |
| 追従リトライ 4 枚 | 採用 | 中央値 61 → 70 |
| 13×16 / 9×12 | 不採用 | 3px/セル で満点 0% / 不安定 |

**マーカーの最適サイズは格子ではなく「コードが何 px/セルで写るか」で決まる**
(11×10 は大きく写るので小さいマーカーで足り、11×14 は小さく写るので大きいマーカーが
要る)。格子ごとにマーカーサイズを変える案は、受信側がヘッダを読む前にマーカーを
見つける必要があるため候補試行が要り、今回は見送った。現状は全格子 24 セル固定で、
5×4 のような小さい格子では幅の半分をマーカーが食う。

## 最終構成の確認 (11×14 / コーナー 24 / 追従リトライ 4 / 露出ロックは 100 枚後、5 本)

92.5 / 75.5 / 74.8 / 72.0 / 75.0 KB/s (平均 78、最小 72)。**最大の空白 140ms、
カメラロック 0 回。** 朝の 11×10 (60 KB/s、44〜75 のばらつき) に対して、平均で 1.3 倍、
最悪値で 1.6 倍。二極化は消えた。

補足: この確認のあと、5×4 でヘッダが 2 コピー入らなくなっていたのを直すため
ヘッダ/較正の行数を 8 → 9 にした (BAND_ROWS)。あわせて 2bit の較正がストリップ
全体 (大半が白) を読んでいたのを較正行だけに直した。いずれもスキャン量の差は 1 行分。

合成テストで見つかった既知の弱点: 8px/セル (近距離) だとマーカーが 192px 角になり、
広域探索の粗い位置合わせ (±96px) がマーカーの内側の縁に掴まってヘッダが読めないことが
ある。実機の 4〜5px/セル では起きていない。近距離運用を詰めるときに見る。

## 2026-08-30: 構図を据え直したら掴めなくなった → 探索のガイドが幅基準だった

カメラを据え直し、送信ウィンドウを縦長 (780×1030) にして 11×14 をモニタの高さ
いっぱいに出した。受信のダンプ画像は四隅マーカーが鮮明で 4.0 px/セル、構図として
申し分ないのに CornerMismatch で 1 枚も掴めない。

切り分け (`vcode/examples/scan_quad.rs`: ダンプに真の四隅を手で与えてスキャン):

- 真の四隅を与えると scan_frame は通る (124/154)。照合・復号は正常
- `locate_code` の推定は中心 (648,680)・1024×960 で、真値 (幅 910 × 高 1360) から大きく外れる
- フォールバックのガイド枠は「幅 × frac」で決めて高さを縦横比から出していたため、
  縦長コードを画角いっぱいに写すと高さが 53px/辺ずれ、粗探索の許容 ±48px を超える
- 手動取得のスケール候補は最大 0.7 で、画角の 76% を占める構図には届かない

つまり**大きく写すほど掴めない**構造だった。ガイドを「画角に収まる最大枠 (contain)
× frac」基準に変え、frac を [0.85, 0.95, 0.72, 0.58]、取得のスケールに 0.9 を足した
(`contain_guide`)。直後に 166 枚/14 秒で追従、検出率 91%。

受信の読み上げ (充填/余白/px/セル) はこの構図で
`充填 幅 76% · 高 86%  4.0 px/セル / 余白 上 4% 下 9% 左 11% 右 13%` と出た。
送信側は静止モード (`--hold`) で合わせられる。

既知の問題: 手動の「今すぐ位置を検出」(thorough) が 1600×1200 / 11×14 で 1 分以上
ブロックし、その間フレーム処理が止まる。自動取得 (light) は数百 ms。要対処。

### 「半分しか取れない」フレームの落ち方は斜めの帯

受信レポートにブロックごとの回収可否 (`block_ok`) を足し、60% 未満のフレームで
どのブロックが落ちたかをログに出した。散らばり (露出・ピント) でも片側 (位置合わせ)
でもなく、**右上から左下への斜めの帯**として落ちる:

```
##########.
########...
#######....
###........
##........#
.........##
......#####
...########
###########
```

スマホは縦持ちなのでセンサーの読み出し (ローリングシャッター) は画像の左→右に進み、
モニタのリフレッシュは上→下に進む。表示の切り替わりの前線は両者が交差する斜めの線に
なり、LCD のスイープ 16.7ms + 応答 + カメラ露光が重なる幅が帯になる。

なお「カメラの実効 fps が送信 fps に近づいて位相がロックする」という仮説は、
11×14 の全 35 本でカメラ fps が 28.4〜29.5 に収まっていて成り立たなかった。
満点率もスループットと相関しない (満点 0% で 92.5 KB/s の回がある)。部分回収が
効いているので、帯が入ること自体は致命的ではない。

### 据え直し後の再現性 (11×14 / 20fps / contain 探索、6 本)

45.7 / 58.9 / 75.1 / 86.4 / 63.5 / 63.0 KB/s (平均 65)。全 6 本で 60% 未満の
フレームは 0〜6 枚、いずれも中央の行に集中する斜めの帯。「全フレーム一様に 45%」の
型 (pos5) は 11 本中 1 回で、再現できていない。

帯の幅を決めるのは LCD の応答時間とカメラの露光時間なので、受信側の露出補正を
マイナスに振って露光を短くすれば帯が狭まるはず、というのが次の実験
(`--es ev` で起動 Intent から渡す)。

### 露出補正 (11×14 / 20fps、各 4 本、ランダム順)

| EV | 実効 KB/s | 平均 | 中央値 | 最小 | 60% 未満のフレーム |
|---|---|---|---|---|---|
| 0 | 57.8 / 67.4 / 97.0 / 79.5 | 75.4 | 73.5 | 57.8 | 2 |
| −1 | 60.4 / 102.1 / 65.8 / 94.9 | 80.8 | 80.3 | 60.4 | 0 |
| −2 | 78.9 / 78.4 / 85.0 / 85.8 | **82.0** | **82.0** | **78.4** | 0 |

露光を短くすると、表示の切り替わりがローリングシャッターの 1 枚に混ざる帯が狭まる
という読みどおり。平均より**ばらつきが縮む**のが効果の本体 (−2 EV で 78〜86)。
モニタの白は 221/255 と明るいので、−2 EV でも 1bit の判定には余裕がある。
camerax の `setExposureOffset` の戻り値は EV ではなく補正インデックス (1/6 EV 刻み)。

追加 (−2 を 6 本、−3 を 4 本):

| EV | 実効 KB/s | 平均 | 中央値 | 最小 |
|---|---|---|---|---|
| −2 (6 本) | 78.9 / 91.8 / 95.6 / 78.4 / 85.0 / 85.8 | **85.9** | **85.4** | **78.4** |
| −3 (4 本) | 5.4 / 92.0 / 88.1 / 72.3 | 64.5 | 80.2 | 5.4 |

−3 は速い回もあるが 4 本中 1 本が 5.4 KB/s に落ちた (暗すぎて余裕がない)。
**既定を −2 EV にした** (`kDefaultExposureOffsetEv`)。据え直し前の最終構成 (72〜93、平均 78)
に対して、平均 86 / 最小 78 で、ばらつきが縮んだぶんが改善。

既定 −2 EV を Intent なしで適用した確認 (3 本): 59.8 / 66.2 / 103.9 KB/s
(ログ `exposure offset -2.0EV -> index -12`)。−2 EV の 9 本合計で平均 83、最小 59.8。
0 EV (57〜97、平均 75) より良いが、据え直し後はまだ 60 台に落ちる回がある。

## 2026-08-30 (続き): マーカー直接検出

探索の起点を「テクスチャ推定 → ガイド枠」から「四隅マーカーを縮小画像から直接探す」に
変えた (`vcode/src/markers.rs`)。狙いは 2 つ: 大きく写しても掴めること (テクスチャ推定は
縦長を画角いっぱいに写すと大きく外す) と、前フレームに依存せず毎フレーム掴み直せること
(手持ちの土台)。

方法: 1/4 縮小画像の積分画像で、外周が黒く周囲が白い箱を大きさ 11 段階 × 位置 2〜3px
刻みで総当たりし、内部の模様 (塗りつぶし / リング / 中央だけ黒 / 半分黒) で 4 種を
見分け、幾何的に整合する 4 つの組み合わせを選ぶ。模様で種別が決まるので、コードが
回転していても四隅が正しい順で出る。1200×1600 で 6ms。

作りながら踏んだこと:
- 塗りつぶしマーカーは内側の小さい箱も条件を満たす → 同点なら大きい箱を採る
- マーカーより大きい箱は外周に白が混ざる → 外周の明るさを点数に入れて弾く
- 小さいマーカー (縮小後 18px) は 1px の位置ずれで落ちる → 箱の縁 1px を見ない
- 候補を 3 件に切り詰める並び順が「不一致」だけだと、縁にまたがる箱が本物を押し出す
- BR の「半分が黒」は回転すると黒い半分がどこにでも来る → 上下左右のうち最も合うもの

検証: 合成 (3〜8 px/セル × 5x4/11x14/13x18 × 180° 回転) と実機ダンプ 2 枚
(いずれも精密化後の四隅から 5px 以内)。

### 格子の天井 (マーカー直接検出後、20fps / −2 EV、各 3 本)

| 格子 | ブロック | 実効 KB/s | 平均 | 満点率 | 追従 scan 中央値 |
|---|---|---|---|---|---|
| 11×14 | 154 | 76.7 / 89.5 / 80.5 | 82 | 62〜70% | 38〜44 ms |
| 13×16 | 208 | 74.5 / 56.0 / 56.1 | 62 | 47〜80% | 42〜64 ms |
| **13×18** | 234 | **131.3** / 90.8 / 86.3 | **103** | 18〜42% | 40〜46 ms |

13×18 (3.3 px/セル 相当) が通るようになった。前回 13×16 が「3px/セルで満点 0%」だったのは
密度の限界ではなく探索の問題だった (マーカー直接検出で解消)。満点率は低いが容量で
押し切って 131 KB/s。

**追従の scan 時間はセル数に比例していない** (11×14 も 13×18 も 40〜46 ms)。
セルのサンプリングより固定費 (回転コピー・閾値・四隅の精密化) が支配的で、密度を
上げる余地はまだある。検出間隔は 60〜80 ms (カメラの 2 枚に 1 枚)。

### さらに密な格子と、13×18 の 15fps (各 3 本)

| 格子 @fps | ブロック | 実効 KB/s | 平均 | 満点率 |
|---|---|---|---|---|
| **13×18 @15** | 234 | 155.8 / 131.4 / 115.4 | **134** | 33〜38% |
| 13×18 @20 | 234 | 103.1 / **164.8** / 86.6 | 118 | 18〜46% |
| 15×18 @20 | 270 | 87.4 / 106.5 / 124.9 | 106 | 27〜42% |
| 13×20 @20 | 260 | 77.6 / 113.7 / 98.7 | 97 | 0〜13% |

13×20 (カメラ側 3.0 px/セル 相当) で満点率がほぼ 0 になり、密度の床はここ。15×18 は
幅が縦長ウィンドウ (780px) に当たって縮む。**13×18 が本命**で、15fps のほうが平均も
最小値も高い。満点率の低い高密度では、混ざるフレームを減らす効果 (fps を下げる)
のほうが枚数の減少より効く。164.8 KB/s は現時点の最良値。

### 計測ファイルを 100KB → 1MB に変更

130 KB/s 台では 100KB は 0.6〜0.9 秒 (検出 10〜14 枚) で終わる。1 枚がファイルの 10% に
なって結果がフレーム単位で量子化され、立ち上がり (初回取得) が所要時間の大半を占め、
定常状態・100 枚追従後の露出ロック・熱の影響が測れない。以降は 1MB (約 8 秒、120 枚)
を標準にし、最終確認は 2MB で行う。100KB の結果は同条件同士の比較にのみ使う。

### 1MB での定常スループットと、受信 1 枚あたりの内訳

1MB (13×18 @15fps) は 107.2 / 82.4 / 96.8 / 87.0 KB/s。100KB の 134 に対して 7 割で、
100KB の値は立ち上がりの瞬間風速だった。fps は 12 (84) / 15 (95) / 18 (65) / 20 (72) で
15 が最良。11×14 @20 は 64.6。

フレームログ: 検出は送信 fps によらず **毎秒 10〜12 枚**で頭打ち (カメラは 28fps)。
ブロック回収率は 92〜97% で、帯の損失は小さい。露出ロックは発動していない。
つまり壁は受信の 1 枚あたり処理時間。Dart 側に計測点を入れた内訳 (30 枚平均):

```
total=64.9ms  scan(frb)=64.9ms  decoder=0.3ms  miss=0/30  rust(rot+dec)=37〜42ms
```

- デコーダ投入 (RaptorQ) は 0.3 ms で無関係
- Rust の実処理 (回転 + 復号) は 40〜45 ms/枚 (13×18、熱で伸びる)
- Dart↔Rust の往復に約 20 ms/枚が消える。Y 面 1.9MB のコピーは Uint8List の
  一括経路 (1〜2 ms) なので、非同期呼び出しの完了が UI スレッドの空きを待つ
  遅延 (描画 1 フレーム ≈ 16 ms) が主と見ている
- 検出できなかったフレームは 100〜270 ms かかるが、追従が安定した区間では 0 枚

次の手は計測ではなく高速化: (1) Rust の復号をブロック単位で並列化 (4 コアで
45 → 15 ms 前後)、(2) Dart 側の待ちを削る (同期呼び出し or UI 更新の間引き)。
両方で 1 枚 20〜25 ms → カメラの上限 25 枚/秒 → 13×18 で 150〜170 KB/s の見込み。

### 注意: 1MB の初回計測はコードの下端がタスクバーに隠れていた

送信ウィンドウを高さ 1030 で y=1 に置き、さらに下へ 2.5% 寄せていたため、コードの
下 2 セルほど (下側マーカーの外周) が Windows のタスクバーに潜っていた。受信の
読み上げは見えている部分から四隅を出すので気づけなかった。指摘を受けて、高さ 1015・
下寄せなしに直し、PC のスクリーンショットで下のマーカーと余白がタスクバーの上に
収まっていることを確認した。上の 1MB の値 (13×18 @15 で 82〜107) はこの状態で
取ったもので、以下で測り直す。

### 据え直し (2 回目) で掴めなくなった 2 つの理由

三脚を再調整したあと、四隅が全部写っているのに掴めなくなった。ダンプで切り分け:

1. **露出補正 −2 EV が位置依存だった。** 新しい位置では白が平均 68 (黒 22) まで沈み、
   コントラストが半分以下になった。0 EV では白 157 / 黒 57。最初の位置で −2 EV が
   最良だったのは、そこで白が 136 残っていたから。カメラの自動露出が何を見るかで
   絶対的な白の明るさが変わるので、固定値の既定は −1 に戻した。本来は白の実測
   (輝度の最大値) を見て補正を追従させるべき。
2. **コードの上端が画角の 2.5% まで詰まると、ヘッダが読めない。** 0 EV でコントラストを
   戻してもマーカー四隅は合うのに HeaderNotFound。ヘッダは最上端の幅 900px の細長い帯で、
   データブロック (20×20 ごとに ±0.5 セルの補正) と違って帯全体を 1 つの位置合わせで
   読むため、レンズの歪みが効く縁では中央がずれる。送信を 0.94 倍にして上に 5% 残すと
   即座に掴めた (105/105)。ヘッダを区間ごとに位置合わせして読むようにすれば
   縁でも読めるはずで、手持ちにも効く改善候補。

また、窓の中でコードを片側に寄せる (dx) と、その側の白い余白が消えて外の暗い壁紙が
隣接し、マーカー検出の「周囲が白い」要件を満たせなくなる。位置は窓の座標で合わせ、
窓は広め (900px) にしてコードは中央に置く。

### 据え直し後の 1MB は熱で比較にならなかった

新しい位置での 1MB (13×18 @15、0.94 倍、−1 EV) は 29.5 / 56.9 / 73.6 KB/s。ただし
1 本目の開始時に BIG コアが 60°C で、追従 scan の中央値が 167 / 92 / 81 ms
(朝は 52〜61 ms) と熱で 2〜3 倍に伸びていた。(直後に 70°C と記録しかけたが、それは
`dumpsys thermalservice` 先頭の「Cached temperatures」を読んだ古い値で、HAL の現在値は
43°C だった。温度は「Current temperatures from HAL」の側を読むこと。)ブロック回収率は 92〜96%
で正常。**受信の 1 枚あたり処理時間は温度で 40 → 120 ms まで変わる**ので、長時間の
連続計測では冷却待ちを挟まないと条件が揃わない。位置 1 との比較は冷えてから取り直す。
処理を並列化して余裕を作れば、熱で伸びても天井に当たりにくくなる。

なお等倍 + −1 EV では 0 枚だったので、掴めなかったのは露出ではなく上端の余白 (ヘッダ帯)
のほうだと確定した。

### 据え直し後、冷えた状態での 1MB (13×18 @15fps、0.94 倍、−1 EV、BIG 43°C、各 30 秒冷却)

92.3 / 95.0 / 69.5 KB/s (平均 86)。追従 scan 中央値 67〜69 ms、ブロック回収率 91〜94%。
位置 1 (82〜107、平均 95) とほぼ同じ水準で、据え直しによる差は誤差の範囲。
熱い状態 (60°C) の 29.5〜73.6 とは明確に違い、温度を揃えないと比較にならないことも確認。

**この日の最終値: 13×18 / 15fps / 1MB 定常 70〜107 KB/s (平均 90)、100KB 瞬間風速の最良 164.8 KB/s。**

## 2026-08-30 午後: 受信の並列化

据え直し (3 回目) の読み上げは `充填 幅 68% · 高 83%、3.1 px/セル、余白 上 9% 下 9%
左 16% 右 16%`。等倍にして上を 6% にするとまた HeaderNotFound になったので 0.94 のまま。
**上端の余白は 9% 程度要る**ことが 2 回再現した。ヘッダを区間ごとに位置合わせして
読むのが本筋。

ブロックの復号を rayon で並列化した (`vcode` の feature "parallel"、Android と Python
で有効、wasm は off)。ブロックは独立で、共有していたのは 4 値用のガンマのヒントだけ
(1bit では無関係) なので、線形カーブ固定で始める順にして共有をなくした。

### 並列化は効かず、追従の 9 割は四隅の精密化だった

ブロック復号を並列化した APK で 1MB: 50.7 / 49.6 / 56.0 KB/s (Rust 58〜66 ms) と、
むしろ悪化 (1 本目は直前の等倍テストの重いフル探索で BIG 74°C)。PC で同じ実画像を
繰り返しスキャンして段階ごとに測ると:

```
scan_frame_tracked 18.7 ms = threshold 0.4 / descend 20.2 / decode_at 1.1〜8 ms
```

追従スキャンの時間はブロック復号ではなく **`descend` (四隅の精密化) が 9 割**。
精密化は既知セル (四隅マーカー + 較正行 + セパレータ) の一致数で採点しており、
マーカーを 24 セルにした時点で既知セルが約 3,300 (16 倍) に増え、2 段 × 2 周 × 4 隅 ×
25 候補 = 400 回の採点 × 3,300 = 1 フレーム 130 万サンプルになっていた。

追従 (四隅がほぼ合っている) の採点セルを斜めに 1/4 へ間引いたところ
**tracked 18.7 → 5.9 ms** (PC)、実画像の回収は 124/154 で不変。粗探索からの精密化まで
間引くと収束が甘くなりヘッダを落とす (合成テスト 2 件) ので、そこは全部使う。

ヘッダ診断 (送信側の正解フレームとビット単位で比較): 上端 2.5% に詰めた構図では、
ヘッダ帯の中央区間が 53〜60% (ランダム同然) で、縦オフセットを ±1 セル振っても直らない。
データの先頭行も 70〜80%、最下部は 95〜100%。**画像の上端はレンズの周辺ボケで解像して
いない**。歪みではないので区間ごとの位置合わせ (実装済み、無害) では救えず、上端 9% の
余白は物理的な要件として残る。ヘッダを太いセル (2×2) で書く形式変更なら救える可能性。

### 追従の精密化を 1/4 に間引いた実機結果 (13×18 @15、1MB、43〜47°C)

92.4 / 99.3 / 103.1 KB/s (平均 98)。Rust の処理 (回転 + 復号) は 40〜55 → 約 31 ms、
追従 scan (FRB 往復) は 67 → 50〜56 ms、検出は毎秒 11.4〜12.9 枚。ブロック回収率は変わらず。

残りの内訳: FRB 往復 55 ms − Rust 31 ms = **約 24 ms が Dart↔Rust の境界**。Y 面 1.9MB の
コピーは 1〜2 ms なので、非同期呼び出しの完了通知が UI isolate の描画の空きを待つぶんと
見て、同期呼び出し (`scan_sync`) で測る。

### 同期呼び出し (scan_sync) の実機結果 (13×18 @15、1MB、45〜47°C)

**111.6 / 104.3 / 114.2 KB/s (平均 110)** で 1MB の新記録。FRB 往復 55 → 32〜37 ms、
Rust の処理も 31 → 18〜22 ms に下がった (UI isolate と Rust ワーカーの取り合いが消えた
ためと見ている)。検出は毎秒 14.8〜16.6 枚で、**送信 15fps にほぼ追いついた** = 次の
壁は送信 fps。20 / 24 fps を測る。

以前「sync にしない (UI isolate をブロックしてプレビューがカクつく)」としていたが、
プレビューはネイティブのテクスチャで Dart を止めても止まらず、重ねている UI は
5 枚に 1 回しか更新していないので、実害より効果が大きい。

### 送信 fps を上げても速くならない → 処理枚数が 34ms 境界で 2 枚に 1 枚

同期版で 13×18 @20fps: 120.1 / 99.0 / 95.2 (平均 105)、@24fps: 92.1 / 90.9 / 85.2 (平均 89)。
15fps (平均 110) が最良のまま。どの fps でも検出は毎秒 14〜16 枚で頭打ち。1 枚 32〜37ms
がカメラの間隔 34ms をわずかに超えるため、次のフレームを 1 枚落として 2 枚に 1 枚の
処理になっている。34ms を切れば処理枚数は 29/秒に倍増しうる。

追従の精密化の候補を 5×5 の正方形から十字 (25 → 9) にした: PC で tracked 5.9 → 2.6ms
(descend 5.1 → 1.8ms)、回収は 124/154 で不変。実機で 15 / 20fps を測り直す。

### 十字候補の実機結果と、次の壁 = カメラ画像の受け渡し

13×18、1MB: @15fps 109.8 / 112.8 / 117.8 (平均 113.5)、@20fps 124.8 / 105.7 / 109.3
(平均 113.3)。追従 scan 30〜31ms、Rust 17〜19ms。ところが検出は毎秒 15〜18 枚のままで、
34ms を切っても処理枚数は倍にならなかった。

統計の「カメラ実効 fps」(Dart のコールバック到着率) を見ると、非同期版では 29 だったのが
**同期版では 13〜16** に落ちている。カメラ画像 (YUV420 の 3 面、約 2.9MB) を
プラットフォームから Dart へ渡す処理自体が UI isolate の時間を 20ms 前後使っており、
同期スキャン 30ms と直列になって 1 枚 50〜55ms = 毎秒 16〜18 枚になっている。
非同期版は受け渡しと Rust が重なるぶん到着は 29 だが、処理が 55ms 超で結局 12 枚。

次の手: スキャンを別 isolate に移し、UI isolate は受け取って転送するだけにする
(TransferableTypedData で Y 面をコピーなしで渡す)。受け渡し 20ms と処理 30ms が重なれば
カメラの 29fps まで処理できる見込み (13×18 で理論 190 KB/s に対し 150〜170)。

### スキャンを別 isolate へ (app/lib/scan_worker.dart)

UI isolate はカメラ画像の受け取り (YUV420 の 3 面、約 2.9MB、1 枚 20ms 前後) だけを
担当し、Y 面を TransferableTypedData でワーカー isolate に移送 (コピーなし) してスキャン
させる。VcodeRx (追従状態) はワーカーの中だけに置き、UI からは scan / acquire /
setLayout / seed / reset の窓口を通す。ワーカーが処理中に届いたフレームは最新の 1 枚だけ
保持し、処理が終わり次第すぐ回す (受け取りと処理を重ねる)。副次効果として、手動の
重い位置検出 (1 分以上) が UI を止めなくなる。

### 別 isolate 版の実機結果 (13×18、1MB、43〜45°C)

@15fps 110.9 / 117.4 / 114.6 (平均 114)、@20fps 129.2 / 94.7 / **131.0** (平均 118)。
FRB を 2 つ目の isolate で初期化するのは問題なく動いた。

ところが処理枚数は毎秒 16〜18 枚のままで、代わりに**カメラの供給が 29 → 40fps に上がった**
(UI isolate が空いたぶん、要求していた 60fps に近づいた)。捨てるフレームにも受け取りで
1 枚 20ms 払うため UI isolate の 8 割がそれに消え、CPU の競合でワーカーの追従 scan が
30 → 40ms に伸びた。処理できるのは毎秒 25 枚前後なので、カメラへの要求を 30fps に
落として供給を処理速度に揃える。

### カメラ要求 30fps の実機結果 (13×18、1MB、44〜54°C)

@15fps 122.1 / 110.2 / 116.6 (平均 116)、@20fps **141.3** / 83.1 / 130.4 (平均 118)。
ただしカメラの供給は 38〜42fps のままで、要求 fps はこの端末では効いていない。
検出は毎秒 14〜22 枚、追従 scan 37〜41ms。20fps は最良値が高いが 83 まで落ちる回が
あり、15fps のほうが安定 (110〜122)。プリセットは 15fps のまま。

**この日の最終値: 13×18 / 15fps / 別 isolate で 1MB 定常 110〜122 KB/s (平均 116)、
20fps の最良 141.3 KB/s。** 朝の 1MB 95 (平均) から 1.2 倍、金曜朝の 60 (100KB) から
数えると定常で 2 倍。

残る壁: UI isolate がカメラ画像の受け取りに 8 割使われている (捨てる 40fps ぶんも払う)。
供給を絞れないなら、受け取りを軽くする (Y 面だけ受ける / ネイティブ側で間引く) か、
受け取り自体をネイティブに寄せる必要がある。

### 送信の操作バーでコードの大きさが変わっていた

操作バーをレイアウトに入れていたため、マウスを乗せて出るたびにビューの高さが変わり、
コードが数 px 伸縮していた (指摘を受けて確認)。バーはレイアウトから外して映像の上に重ね、
かつバーの領域は常に描画から除外する (出入りで大きさも位置も変わらず、コードがバーに
隠れもしない)。そのぶんコードは 4% 小さくなるので、構図は取り直した
(22:33 の据え直し: 充填 幅 68% · 高 81%、3.1 px/セル、余白 上 9% 下 11% 左 17% 右 15%)。

### 最終値 (22:33 の構図、別 isolate、13×18、1MB、各 3 本)

| 送信 fps | 実効 KB/s | 平均 | 最小 | 検出 枚/s | 追従 scan |
|---|---|---|---|---|---|
| 15 | 104.7 / 114.8 / 115.3 | 112 | 105 | 16〜22 | 37〜55 ms |
| **20** | **131.2 / 135.4 / 147.2** | **138** | **131** | 16〜22 | 38〜41 ms |

受信が毎秒 22 枚処理できるようになったので、送信 20fps が 15fps を上回り、しかも安定
